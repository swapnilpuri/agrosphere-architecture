## Recommendation and priority

Choose **Operations-owned, SIMULATED crop-health alerts with a durable estate inbox and an in-app badge** as the next bounded increment. Start with existing human-reported HIGH/CRITICAL incidents that are OPEN or IN_REVIEW. Users pull the inbox through authenticated Gateway requests; personal read state and shared manager acknowledgement are separate. This provides a concrete use for locally delivered II-1 without introducing device identity or a recipient directory.

This is an estate audience, not addressed delivery to named people. Eligible users see the same estate alerts after signing in; the system does not know every eligible account, prove anyone has seen a badge, or reach absent users. If the owner requires assigned recipients, email/SMS/push, timed escalation or guaranteed attention, defer this scope and review recipient governance/delivery first. AN-1 would partially satisfy the notification portion of FR-06 only under this explicit channel limitation. Parent Milestone 3, M2 and production acceptance remain open.

## Scope, rules and exclusions

AN-R01: Provide a persistent estate-scoped alert inbox, exact scoped counts and a selected-estate badge. Only SIMULATED incident evidence is eligible. No free-text alert composition.

AN-R02: Versioned rule CROP_HEALTH_HIGH_V1 qualifies an incident when provenance=SIMULATED, status in OPEN/IN_REVIEW and human-entered severity in HIGH/CRITICAL. This is a review-priority rule, not an automatic diagnosis, measured risk or emergency response claim. LOW/MEDIUM and CLEAR inspections alone do not alert. A FOLLOW_UP inspection alerts only through its linked qualifying incident, once.

AN-R03: Maintain at most one alert identity per incident/rule version. First qualification starts attentionVersion=1. Leaving eligibility makes the alert INACTIVE with a reason (RESOLVED, VOIDED or BELOW_THRESHOLD). Returning from nonqualifying state or escalating HIGH to CRITICAL starts a new attention version and clears current shared acknowledgement. Same-severity amendments/corrections, category changes, HIGH-to-HIGH triage and CRITICAL-to-HIGH reductions update current facts without resetting read/ack state. Corrections that cross the threshold do change eligibility. A resolved/voided incident never remains ACTIVE.

AN-R04: Read means an explicit per-subject receipt for the current attention version; opening a screen or fetching a count is not read evidence. Acknowledged means a manager explicitly accepted attention for the current alert episode; it does not triage, resolve, assign or edit the source incident. Reading never acknowledges. Acknowledging also records that manager's own read receipt. Another manager's acknowledgement is shared; personal unread can remain true. Neither action promises follow-up completion.

AN-R05: Derive alerts only from future accepted incident revisions after enablement. No migration/backfill/seed/replay that creates historical alerts. An older incident's next accepted command may first qualify it; eligibility is evaluated on that command's post-state. Persist sourceVersion and ruleVersion. No alteration of existing source receipts/revisions/events or records. Existing II-1 zero totals were historical measured observations, not a current count or a precondition.

Exclude addressed/user-directory delivery, emails, SMS, browser/mobile push, SSE/WebSocket, outbound webhooks, sound, desktop notifications, recipient contact capture, subscriptions/preferences, assignment, escalation timers/digests/snooze, custom thresholds/rules, worker/attendance alerts, sensor/weather alerts, Analytics/AI, automated agronomic advice, offline browser persistence, bulk read/ack/export, attachments and geometry changes. Exclude REAL alerts, account/role/credential changes, private configuration access and any existing-stack upgrade/deployment. No message will be sent to anyone during planning or testing outside generated disposable fixtures.

## Data model, transactions and authorization

Operations owns additive tables/migration (next available version after V5, rechecked at implementation). No new service/repository/database and no cross-service SQL. Suggested logical records:

| Record | Minimum fields / invariants |
|---|---|
| crop_health_alert | alertId UUID; incidentId UUID unique with ruleVersion; estateId/blockId canonical UUID; ruleVersion; sourceVersion; alertVersion; attentionVersion; ACTIVE/INACTIVE and reason; current category/severity/status; provenance SIMULATED; observedAt; raisedAt/attentionAt/updatedAt UTC microseconds; current acknowledgedAttentionVersion/time/subject nullable. Retain no report text. Source incident remains authoritative. |
| alert_transition | Unique alertId/alertVersion; triggering sourceVersion, ruleVersion, before/after eligibility/attention, fixed transition kind/time/correlation. Manager/auditor history only. No copying source actor/revision reasons. |
| alert_read | Primary key (alertId, issuer, signedSubject); highest readAttentionVersion and server readAt. Never accept subject/issuer from a request body. Monotonic, bounded by current attentionVersion; role/scope rechecked for every write/read. No all-recipient rows or delivered flag. |
| alert_acknowledgement | Immutable alertId/attentionVersion, actor issuer/subject, server acknowledgedAt and command identity; at most one shared first acknowledgement per attention version. New attention invalidates current acknowledgement, preserves old evidence. |
| alert_command | Feature-scoped actor issuer/subject + UUID Idempotency-Key; normalized method/path/body hash, original status/body and recordedAt. Same command returns original success after current authorization; mismatched reuse 409. No tokens retained. |

Persist subject values as opaque strings under the configured trusted issuer, not username/email/worker UUID. Ordinary views expose only the caller's read state and shared acknowledgement boolean/time. Acknowledgement actor is protected history. Rule/alert timestamps are server UTC instants; display using source estate timezone. Preserve observedAt separately from alert creation time; backdated source reports do not backdate notification creation.

Recommended production path: deterministic local rule evaluation in the same Operations transaction as each accepted incident revision, source outbox and source command receipt. It receives incident before/after snapshots and revision kind through an internal application port; it does not query another service or call HTTP/broker in the transaction. Existing source idempotent replay does no new rule work. Unique incident/rule and sourceVersion guards prevent duplicate effects. An alert failure rolls back the whole source command: this added availability coupling is an explicit AN-D05 tradeoff requiring review. Do not implement a second broker consumer as well.

Preserve lock order inspection -> incident -> alert -> alert-specific rows. Read/ack commands lock alert only, never subsequently lock source, so source commands cannot deadlock against reverse lock acquisition. Under that lock, source eligibility changes and read/ack races serialize; expected alert/attention versions reject stale ack. Own read commands compare current attentionVersion; older read requests must conflict rather than mark a new episode read. Source revisions update sourceVersion and increment alertVersion for an existing alert even when attention does not change. A successful shared acknowledgement also increments alertVersion and records a protected transition; personal read markers do not increment the shared alertVersion. No mutable alert state is trusted from the browser.

|---|---|---|---|---|---|
| List/count/detail/source link | Yes, explicit estate | Yes | Yes | Yes | Deny |
| Mark own read | Yes | Yes | Yes | Yes | Deny |
| Shared acknowledge | Yes | Yes | Deny | Deny | Deny |
| Protected transitions/ack history | Yes | Yes | Deny | Yes | Deny |
| Inspect others' read state / select recipients / edit rule | No endpoint | No endpoint | No endpoint | No endpoint | Deny |

Reuse existing positive crop-health grants, not legacy role unions: PLANTATION_ADMIN, AGRONOMIST, FIELD_WORKER and VIEWER alone grant nothing. Multiple roles can grant an explicit allowed capability. Validate issuer/audience/sub/role/estate independently at Operations and Gateway. PLATFORM_ADMIN is not automatically subscribed to every estate; it must select an estate. SQL filters apply before list/count/history and before joins; missing/foreign object IDs uniformly 404 after feature-role check, explicit denied estate 403. Reauthorize current role/scope before receipt replay; no replay after downgrade. Source API/deep-link permission remains independent. Current signed claims govern until token refresh/expiry; instantaneous account revocation is not claimed or solved here.

Privacy gate AN-D07 must cover actual signed subjects as well as SIMULATED source metadata, read/ack audit, receipts, logs and backups. Generated identities may be used in isolated tests. No owner-account/live rollout until a separately approved implemented subject-data policy exists. Proposed test evidence lifetime follows disposable resource teardown; no numeric live retention/deletion values are invented. No purge job or cascade deletion is authorized by this package.

## Proposed API and event design (prose only)

Author executable artifacts only after design/implementation approval. Six additive Operations operations, proposed under /api/v1/alerts; preserve all 58 existing operations, payload bytes and independent producer/Web pins. Exact candidate acceptance and independent local release must precede promotion/pinning; no future release number is assigned here.

| Method / path | Input and result |
|---|---|
| GET /api/v1/alerts | estateId required; state ACTIVE default, optional unreadOnly/unacknowledgedOnly/severity/blockId; page >=0, size 1–100 default 20. Stable attentionAt DESC, alertId DESC. Return scoped content/page/size/totalElements and server generatedAt. No arbitrary sort or unbounded offset (propose page*size <=10000). |
| GET /api/v1/alerts/counts | estateId required. Return activeTotal, activeUnreadForMe, activeUnacknowledged, generatedAt from one scoped consistent snapshot. No global recipient totals. |
| GET /api/v1/alerts/{alertId} | Current minimal alert, source reference/version, alertVersion/attentionVersion, caller read state, shared ack state. No source report text. |
| POST /api/v1/alerts/{alertId}/read | Closed body attentionVersion; UUID Idempotency-Key required. Record own read only for displayed current attention; 200 original-success receipt on replay. Already read same attention with a new key returns current success without another history effect. |
| POST /api/v1/alerts/{alertId}/acknowledgements | Closed body expectedAlertVersion, attentionVersion; UUID Idempotency-Key required. Manager only, ACTIVE only; atomically shared acknowledgement + own read + immutable evidence + receipt. Another manager already acknowledged same attention returns 409 and refreshes, not a second acknowledgement. |
| GET /api/v1/alerts/{alertId}/history | Protected transitions/ack history, page/size bounds as above; never other people's read markers. Stable server revision ordering. |

All positive versions fit the existing signed-int64 convention; initial alertVersion=1; executable examples must preserve that rule. Closed shapes reject unknown fields, caller-selected actor/recipient/provenance, arbitrary text, malformed UUID/time/filter/oversized input (400); wrong feature/scope 403, absent session 401, foreign/missing ID 404, stale/inactive/conflicting key 409, unavailable dependency 503. Preserve common problem/correlation handling. Read/ack are SIMULATED-only; cannot bypass source restrictions. Concurrent counts/list may naturally differ across separate requests; generatedAt communicates observation time. Require no-store, transport bounds, existing CORS/idempotency forwarding and limiter/timeouts.

No new shared event family is needed for the proposed in-process rule/inbox. Existing CropHealthIncidentReported/Changed continue unchanged via their original outbox; no notification subject or acknowledgement actor is added to shared events. Internal alert-transition evidence is not a public domain event or delivery receipt. Broker outage retains existing source relay recovery and does not delay committed inbox visibility. No new binding or queue consumes the existing acceptance sink.

If asynchronous alert evaluation is preferred at review, replace AN-D05 and re-review the plan: a dedicated bounded consumer queue/DLQ, accepted event pins, atomic eventId dedup/projection writes, aggregateVersion stale/conflict/gap handling, VOIDED tombstones and authorized reconciliation would be mandatory. Never ACK before durable effects, infer missing states, or assume linked events arrive together. This alternative is excluded from the recommended implementation estimate/scope, not silently added alongside it.
