## Baseline and service boundaries

Operations uses Java 25, Spring Boot 4.0.9, immutable Java records/domain rules, application ports, JDBC and local Spring transactions. Preserve the existing toolchain and explicit JUnit contexts. Retain TappingSchedule, TappingAssignment and TappingRecord fields, tapping workflow and all existing API/event contracts. Refer to TappingRecord.id; obtain its assignment by internal FK and require COMPLETED with actualTreeCount > 0. No mutable 3A state is added to permit collection. Estate owns canonical estate/division/block, active RUBBER classification and timezone. Spatial owns geometry; it is not called to validate production. Analytics will own projections later; this increment supplies live operational SQL summaries only.

## Aggregate and model

LatexCollection is the aggregate root. It owns id, tappingRecordId, assignmentId, immutable attribution (estateId/blockId/workerId/tappingDate), divisionIdSnapshot, blockVersionSnapshot, estateVersionSnapshot, estateTimezone, masterValidatedAt, collectionReference, optional replacementOfCollectionId, collectedAt/collectionDate, wetLatexKg and weight evidence, dataProvenance, status, selectedMeasurementId, dryRubberExactKg, dryRubberKg, calculationPolicy, version and server audit fields. New roots start version=0. Every non-replay mutation increments exactly once. Collection identity, execution link, attribution, provenance, reference and snapshot metadata never change.

DrcMeasurement is an immutable child with id, collectionId, introducedVersion, percent, measuredAt, method, sourceReference, optional sampleReference/instrumentReference, provenance, recordedAt and recordedBy. Only one measurement is selected as current. A replacement appends a child and switches the pointer through an adjustment; old samples and results remain readable. No unqualified latest-by-time selection and no averaging. CollectionAdjustment records approved version, prior version, command type CORRECT/VOID, reason, approvedBy/approvedAt, correlationId and immutable before/after revision references. Approval means a manager-authorized command was successfully applied; it is not an external business approval record.

CollectionRevision is a complete immutable snapshot per root/version, including current measurement evidence, input/derived values, attribution and audit actor/time. Version 0 is creation; first measurement also produces a revision (not an adjustment); corrections/voids produce both. Revision snapshots, not overwritten root columns, supply history. Original root creation evidence remains in version 0. Restrict update/delete on append-only tables for the runtime role; only operational root fields, outbox delivery state and command reservations may be updated through their respective adapters.

Application ports: LatexCollectionRepository (scoped reads, conditional save, evidence append and summary), CollectionReferenceValidation (typed Estate validation result), CollectionEventWriter (explicit event version and immutable snapshot), and CommandReplayStore. Application service coordinates permission, reference lookup, time/range validation and local transaction. Domain rules own state/calculation; JDBC owns no business decisions beyond constraints and conditional writes. Reuse JWT/correlation/error/clock infrastructure. Extend the Estate adapter with a typed collection-specific result; keep the existing EstateValidation.validate method and its 3A behavior intact.

## Invariants and lifecycle

| Command | Preconditions | Atomic resulting state |
|---|---|---|
| Create | Eligible completed execution; authorized actor; canonical active estate/rubber block belongs to execution estate; valid source/time/mass; new reference | PENDING_DRC, version 0, selected measurement/dry values null, creation revision + Recorded.v2 |
| First DRC | PENDING_DRC, observed version; supervisor/management; matching provenance and valid measuredAt/percent | CALCULATED, next version, immutable measurement, derived values, revision + DrcMeasurementRecorded.v2 |
| Correct | PENDING_DRC or CALCULATED; observed version; estate manager/admin; nonblank reason and actual change | Apply permitted patch, optional replacement measurement, recompute atomically, next version, adjustment + revision + Adjusted.v2 |
| Void | Pending or calculated; observed version; estate manager/admin; reason | VOIDED, next version, adjustment + revision + Voided.v2; retain last dry values/evidence but summary contribution zero |
| Replay | Existing key, same actor/scope/normalized command, current authorization still permits original command | Original HTTP status/body/Location, no state/version/history/event change |

Any other state transition returns 400. Applying a second initial measurement requires the correction path; voiding a voided record with a new key is invalid. Empty/no-op corrections return 400. Removing DRC is not allowed: erroneous DRC is replaced with supported evidence or the collection is voided. Changing mass alone uses selected DRC and recalculates; changing collectedAt must preserve measuredAt >= collectedAt or supply a replacement in the same command. Corrections can adjust historical collection date, with immutable previous dates available in revisions. Root remains VOIDED forever. Replacement collections must reference a voided collection of the same execution/provenance and require manager authority; references remain distinct. Do not create a cross-service FK.

All accepted timestamps have an explicit offset and must be exactly representable at microsecond precision (R01). Fractional digits after the sixth position must all be zero; extra trailing zeros may be normalized without loss. Reject any nonzero digit beyond the sixth position rather than silently truncate. UTC instants are persisted at microsecond precision. Require completedAt <= collectedAt <= receivedAt, measuredAt between collectedAt and receivedAt, and derived collectionDate >= tappingDate. observed time is preserved, receivedAt/approvedAt are server instants. A past collectionDate requires backdateReason (1..2000 characters); corrections always require reason. Initial creation fetches current canonical timezone and snapshots it; corrections derive date using that stored zone. No upper backdating window or invented DRC exists.

## Calculation and summaries

Policy DRC_KG_V1: parse decimal JSON number tokens directly as BigDecimal (no intermediate double); wet kg accepts mathematical scale <=3 and range 0.001..999999.999, DRC scale <=2 and range 0..100. Trailing zeros beyond scale may be normalized if value is exact; nonzero excess digits fail before database cast. Use exact multiplication then division by decimal 100, with exact scale 7 kg maximum. Store dryRubberExactKg at scale 7; dryRubberKg = exact.setScale(3, HALF_UP). Do not round DRC or wet input into validity. Output canonical decimal JSON numbers with kg scale 3 and DRC scale 2; source string formatting is not evidence of greater accuracy. Do not use MathContext limiting intermediate precision. Upper bound dry mass equals wet mass at 100%. Missing DRC keeps both derived columns null; zero measured DRC yields explicit 0.000.

| Wet kg | DRC % | Exact dry kg | Recorded dry kg |
|---|---|---|---|
| 125.500 | 32.40 | 40.6620000 | 40.662 |
| 0.001 | 50.00 | 0.0005000 | 0.001 |
| 1.005 | 50.00 | 0.5025000 | 0.503 |
| 999999.999 | 100.00 | 999999.9990000 | 999999.999 |
| 10.000 | absent | null | null |
| 10.000 | 0.00 | 0.0000000 | 0.000 |

Summary knownDryRubberKg sums current per-collection rounded dryRubberKg in unbounded PostgreSQL numeric / arbitrary-precision BigDecimal. No row truncation before totals and no re-rounding until output scale 3. This chosen accounting basis reconciles totals to record values: two 0.001kg/50% lots total 0.002kg recorded dry, although rounding their exact sum once would yield 0.001kg. Do not mix those bases. WeightedDrcPercent = sum(dryRubberExactKg) * 100 / sum(calculated wetLatexKg), HALF_UP scale 2, null for no calculated wet mass. It includes only measured, nonvoided rows and is labeled measured-only; no arithmetic average of percentages. Summary totals do not claim lab accuracy.

Each summary row includes provenance and the selected group key, activeCollectionCount, pendingDrcCount, calculatedCollectionCount, voidedCollectionCount, totalWetLatexKg (nonvoided), pendingWetLatexKg, calculatedWetLatexKg, knownDryRubberKg (zero for empty), weightedDrcPercent and isComplete (pendingDrcCount=0). Unknown production stays explicit even when knownDryRubberKg=0. Empty groupBy=total returns one zero-valued row per requested provenance (or both allowed provenances); empty grouped queries return no rows. Division grouping uses the creation snapshot, worker uses execution worker, and date means collectionDate, never measurement date or server receipt date. Read committed single SQL statement/CTE gives one consistent query snapshot; there is no cross-request snapshot/export guarantee. History is fetched separately. Fixed attribution plus revisions permits old/new event reconciliation when correction moves dates.

## Authorization and reference checks

| Role | Read/list/history/summary | Create weight | First DRC | Correct / void / replacement |
|---|---|---|---|---|
| PLATFORM_ADMIN / PLANTATION_ADMIN | All | All | All | All |
| ESTATE_ADMIN / ESTATE_MANAGER | Trusted estates | Scoped | Scoped | Scoped |
| FIELD_SUPERVISOR | Trusted estates | Scoped | Scoped | Denied |
| FIELD_WORKER | Own execution worker + trusted estate | Own | Denied | Denied |
| AUDITOR / VIEWER | Trusted estates | Denied | Denied | Denied |

Use positive operation permissions: a worker also holding VIEWER/AUDITOR retains own create permission but gets no other-worker writes. Read roles can broaden scoped reads as in 3A. Never infer write permission from Access.workerOnly (which is a read filter helper); build dedicated collection policies. Derive IDs from stored execution and explicitly validate requested filter intersections. A worker filter for another worker returns 403; absent filter forces sub in SQL. Unauthorized existing objects return 403, missing local IDs 404, following current convention. No response exposes foreign payload/history on conflict or replay. Validate replay authorization again even if estate access has since been revoked.

At creation delegate bearer + correlation to trusted, timeout-bounded, no-redirect Estate GET /api/v1/estates/{id} and /api/v1/blocks/{id}. Validate response UUIDs, estate ownership, ACTIVE statuses, RUBBER, valid ZoneId, nonnull UUID divisionId and nonnegative master versions. Source divisionId directly from canonical block response; no new division endpoint or lifecycle assertion. Record both versions and masterValidatedAt. No cross-service transaction: reference may change after validation, so snapshot what was validated, never claim global serializability. Failure mapping is inherited from 3A (401/403 -> 403, missing/inactive -> 422, malformed/timeout -> 503); missing required fields is malformed, not guessed. Existing collection reads, DRC, corrections and voids use stored context/current JWT and do not require live or still-active master data. This allows repair during Estate outages/deactivation without authorizing a new collection.

## Command replay and transaction algorithm

Idempotency-Key must be UUID; scope is (authenticated sub, key) across all collection write routes. Normalize the typed command including HTTP method, canonical path/resource, expected version, semantic request fields, decimal values (not JSON whitespace), and explicit absent/null meaning; exclude bearer/correlation transport metadata. Persist SHA-256 of canonical representation plus normalization policy version 1, not tokens. Retain reservation/result indefinitely for now. Different actor's key is a separate namespace; permanent execution/reference uniqueness remains the secondary defense.

1. Authenticate, parse/validate syntax and authorize the operation against local execution/root. Do not allow replay to bypass current policy.
2. Look for committed replay; same hash returns original status/body/Location. Mismatch returns 409. Do this before external calls, stale-version or lifecycle checks so an ambiguous retry remains resolvable after later changes/master outage.
3. For new creation, obtain canonical Estate snapshot outside the DB write transaction with bounded calls. Other commands need no master fetch.
4. Begin local transaction; insert command reservation under unique actor/key, then recheck local eligible record or root and scope. Concurrent reservation insert waits; after competing commit, compare its hash and return its result. Bound lock wait; timeout returns retryable 409. Never leave a committed reservation without response. Rollback reservations on any failure. If reservation is reclaimed after a failed transaction, revalidate new external data where required.
5. For existing root, conditional UPDATE WHERE id=? AND version=?; 0 affected rows -> 409. Create locks/reads completed assignment and record for eligibility (terminal 3A state is immutable). Insert root/evidence/revision/adjustment as applicable. Enforce reference uniqueness even with different keys/actors.
6. Write one immutable event envelope/outbox row, serialize successful response and persist status/Location/body + affected collection ID in command row; commit together. Serialization/outbox/history failure rolls everything back. Return only after commit; response transport loss is recovered with original key.

No automatic HTTP retry with a different key. Failure responses are not permanently cached; a retried command after failed validation may be evaluated afresh. Successful cached response includes original revision/version even after later edits, documented as a command receipt; GET returns current state. New response correlation header reflects the current request while original event/correction correlation remains historical. Compare-and-set prevents concurrent measurement/correction/void races; version check remains mandatory even if a new key repeats a past payload.

Add composite root FK (id,selected_measurement_id) -> drc_measurement(collection_id,id), DEFERRABLE INITIALLY DEFERRED; null pointer allowed pending. Measurements reference root, so create root pending then append measurement/update pointer within one transaction. No cascading delete. Revision/adjustment FK constraints may be deferred to permit natural insert order. Existing 3A tables need no new columns or altered uniqueness. Verify root tapping_record_id/assignment_id and attribution agree by application lookup; SQL FKs alone do not prove these copied fields match. Add a root write trigger validating this join and completed/nonzero eligibility on INSERT; do not add uniqueness or fields to 3A tables. Direct SQL writes outside adapters are not a supported correction interface.

Constraints: version/master versions >=0; trim-nonblank text within declared bounds; collection reference normalized uppercase ASCII [A-Z0-9][A-Z0-9_-]{0,63}, with unique(tapping_record_id,collection_reference) across all statuses; wet >0 and <=999999.999; percent 0..100; provenance REAL/SIMULATED; valid method/status enums; collected_at <= updated_at (creation sets updated_at=created_at, later approved corrections set server updated_at), collection_date >= tapping_date; selected measurement/dry/policy all null for pending; all nonnull for calculated; VOIDED retains either valid previous shape. SQL CHECK ensures dry_rubber_exact_kg >=0 and <=wet_latex_kg, rounded dry equals round(exact,3). Application enforces exact formula using selected measurement, its ownership, provenance, chronology and stored zone/date consistency on each write. Database cannot validate a dynamic canonical Estate state. numeric casts can round invalid input, so reject excess precision before SQL. Snapshot JSON must be object; enum/formula validation requires application/domain tests. Runtime role cannot UPDATE/DELETE measurements/revisions/adjustments or completed command results; service migration owner provisions tables and grants accordingly. Deferred command-completion trigger and append-only guards belong in V3, not manual active-database edits.

Indexes: permanent execution/reference unique index; root (estate_id,collection_date,id) for scope/page; (estate_id,block_id,collection_date,id), (estate_id,division_id_snapshot,collection_date,id), (estate_id,worker_id,collection_date,id), (tapping_record_id,id); partial (estate_id,collection_date,id) WHERE status='PENDING_DRC'; drc_measurement(collection_id,introduced_version); revision/adjustment composite keys cover history. Evaluate plans on synthetic volume before adding further summary indexes. Existing outbox_due and outbox identity are reused; event_version column already supports v2. No cross-database SQL, JPA model sharing or sibling source dependencies.

### Migration and runtime roles

Current Compose uses agrosphere_operations as both database owner and runtime login, and Flyway inherits datasource credentials. Proposed 3B isolates the runtime as agrosphere_operations_app (NOSUPERUSER, NOCREATEDB, NOCREATEROLE, no DDL) in the same Operations database; retain agrosphere_operations as migration owner. Configure dedicated spring.flyway.user/password through private FLYWAY_USER/FLYWAY_PASSWORD and DB_USER/DB_PASSWORD for the runtime. Grant runtime SELECT/INSERT/UPDATE needed for existing tapping/outbox/processed_event, plus new root/command writes, and SELECT/INSERT only for immutable evidence. Completed-command immutability additionally needs a row guard because initial reservation completion legitimately uses UPDATE. No cross-service access or public schema CREATE is granted. V3 uses the provisioned runtime role, grants and deferred guards; grants are tested with real runtime connections. Provision a disposable/test runtime login before migration; existing environments require a documented additive operator step rather than rerunning bootstrap/reset. Credentials never enter committed examples. The old3A rollback drill explicitly uses the runtime role with a valid datasource; its Flyway path remains owner-configured or disabled after migration validation. This is a proposed technical extension, not a claim that role separation exists today.

## Upgrade, rollback and recovery boundaries

Test fresh V1->V2->V3 and populated 3A V2->V3 in disposable PostgreSQL, preserving records, published and pending outbox rows, Flyway checksums and existing uniqueness. One transactional V3 migration includes DDL/constraints/triggers/grants; inject a failure to verify no partial schema or Flyway success row remains. No backfill invents collections from tree counts or legacy example events.

Application rollback: stop 3B writes/relay, reconcile pending publication, run the previous 3A application against additive V3 schema in an isolated drill; preserve all 3B tables/evidence. Existing relay reads event_version dynamically and can transmit stored v2 payloads, so restrict publication/consumer readiness explicitly during rollout. No automatic Flyway down migration or dropping data. Database reversal after data exists requires a reviewed backup/restore/forward-fix plan and outage boundary; rehearsal restores an isolated backup only. Do not run destructive rollback against active databases. Keep 3B events for future consumers even if application is rolled back.

Broker recovery follows ADR 0012: confirm + no mandatory return before mark published, capped exponential retries, retained FAILED rows, operator-controlled reset of selected IDs after routing/broker repair. Never regenerate event IDs. Reconciliation compares current root to its latest revision and outbox event aggregate/version; inspect gaps without logging sensitive payloads. Readiness is not a certification of publication. Downstream uses transactional eventId dedup + highest collection version; later correction replaces a snapshot contribution, and VOIDED contributes zero. No downstream consumer is implemented here.
