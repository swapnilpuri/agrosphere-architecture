## Rollout and operational sequencing

1. Review contract/ADR/business defaults and independent version changes. Preserve released v1 artifacts and add the required separate collection v2 sink/bindings. Build each image independently and archive tested contract hashes.
2. In a disposable environment, migrate Operations V2->V3 under the service migration owner; verify runtime-role restrictions. Run a previous 3A image against V3 before enabling new writes. Provision no new cross-service database permission.
3. Deploy candidate Operations with pinned reviewed contracts, verify existing tapping and health first, then collection commands with SIMULATED inputs. Gateway predicate already covers routes; verify Idempotency-Key/bearer/query/correlation forwarding and reject invalid JWTs at both hops.
4. Exercise committed pending outbox during broker outage, confirms/unroutable failures, same-ID replay and correction/void reconciliation. No consumers are promised; preserve durable event evidence for future independently scoped consumers.
5. Roll back application in the isolated drill by stopping new writes, reconciling outbox state and using prior 3A application without dropping V3 evidence. Restore backups only into separate disposable DB for verification. Forward fix is preferred after production data exists.

Actual remote releases or production deployment are outside the current authorization. Verify_collections.py must use random project names, generated credentials, separate loopback ports and volumes, never developer .env/local-secrets. Cleanup resolves/verifies only resources belonging to that test project. No broad docker prune or active-database reset.
