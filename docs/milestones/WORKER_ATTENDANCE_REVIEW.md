Date: 2026-10-28 (America/Chicago). Status: PROPOSED, owner review required. Inspection/planning is authorized; executable contracts, application code, migrations, realm changes and implementation are not authorized by this package. WA-1 is a planning identifier, not an accepted roadmap milestone or release number. Existing 3B approvals remain valid only within their recorded scope.

## Assessment and evidence

Recommendation: deliver a minimal estate worker register and supervisor-entered daily roll call together. Registration is a prerequisite for attendance. Separate operational identity from authentication, preserve existing tapping/collection attribution, and collect no actual worker data until the owner has accepted its purpose, fields, access and retention policy. Rubber plantations in countries including Gabon and Malawi are the target context; no plantation names, workforce sizes, employment arrangements or boundaries are known.

## Recommended scope and requirements

| ID | Proposed requirement |
|---|---|
| WA-R01 | Register an estate-scoped worker with a canonical UUID, estate-local code, display name, explicit REAL/SIMULATED provenance and dated active registration periods; no login required. |
| WA-R02 | View/search/edit minimal worker details and close/reopen active periods with audited reasons and observed versions; no hard delete, cross-estate transfer or global person search. |
| WA-R03 | For a selected estate-local date, show the eligible register and independently record PRESENT, ABSENT or EXCUSED for each person. UNMARKED means missing evidence, never automatic ABSENT. |
| WA-R04 | Keep one durable daily attendance identity per estate/worker/date; record authenticated actor and server time separately from the observed date, with reasoned manager correction/void and immutable history. |
| WA-R05 | Enforce explicit role and trusted estate permissions before queries, counts, histories and replay. Personal details and attendance are not ordinary map-viewer data. |
| WA-R06 | Use current ports/adapters, service-owned additive migrations, atomic command receipts/revisions/outbox and independently reviewed versioned Contracts additions. |
| WA-R07 | Keep REAL and SIMULATED separate in queries, roster coverage and summaries. Supply SIMULATED-only fixtures; do not seed the owner's existing databases or infer real people from account names. |
| WA-R08 | Supply accessible Web flows, conflict/ambiguous-response recovery and clear partial-save/coverage feedback through Gateway only. |

Explicit exclusions: shifts, hours/overtime, check-in/out clocks, breaks, GPS/geofencing, photos/biometrics, national IDs, birth dates, contact details, health/leave reasons, pay rates/payroll, employment classification/contracts, productivity rankings, contractor organizations, bulk import/export, attachments, anonymous workers, mobile/offline sync, worker self-service, account provisioning/linking, automatic absence, and attendance prerequisites for tapping or payment. A daily PRESENT assertion does not prove hours, location, completed tapping, entitlement to wages or legal compliance. National rules/retention obligations are not asserted by this engineering proposal.

No surveyed boundary or field geometry is needed for roll call. Optional default division is organizational context only; no block attendance or finer block entitlement is inferred. The first UI is online and supports narrow screens but makes no offline persistence promise. Field connectivity, actual languages and roster size remain review inputs, not assumed facts.

## Screen flows

Proposed navigation: **Workers** (`/workers`) and **Attendance** (`/attendance`) within the existing authenticated shell. These are future routes. Preserve estate selection, sidebar style and unsaved-change protection; load accessible estate context for supervisors/auditors through feature permissions without granting estate-edit access.

1. **Workers list:** choose an accessible estate; filter active-on-date/all and code/name; show code, display name, optional division, registration state and provenance. Empty state says no registered workers and offers Register only to managers. Loading, denied and failed states remain distinct. No initial REAL fixtures.
2. **Register:** enter code, display name, first active date, optional division and explicit provenance. Review entered facts and estate before Save. One successful request opens detail with UUID/version; ambiguous response retains the idempotency key and offers retry/reconcile. Duplicate code conflicts preserve the form. A name match warns for review but never merges people automatically.
3. **Worker detail:** current details, dated active periods and manager-only revision history; edit name/division with observed root version and a reason. Close active period using the exclusive end date and reason; reopen with a new nonoverlapping period. Historical attendance is retained. No button creates a Keycloak account or changes tapping identity.
4. **Daily attendance:** select estate-local date (default today using canonical estate timezone), then division/provenance filter. Show eligible workers and current attendance side by side. Each row starts UNMARKED unless evidence exists. Choose PRESENT/ABSENT/EXCUSED and Save row. EXCUSED records no medical/leave category. No inferred values or "mark everyone absent" action. No multirow atomic submission in WA-1; each row clearly shows saved, saving, failed or unsaved.
5. **Review coverage:** show eligible, marked, unmarked and voided-evidence counts separately by provenance, plus dated observed records that no longer match a current roster view. Any division filter is labelled current worker division; history uses immutable registration context. No attendance rate or productivity KPI in WA-1. A legitimate empty roster differs from dependency/load failure.
6. **Attendance detail/history:** supervisor can read current daily evidence; manager/auditor can inspect revisions. Manager corrects status with a reason or voids a mistaken entry. Estate/worker/date/provenance are fixed. Wrong person/date requires voiding the wrong evidence and separately recording the right identity. Re-recording a voided day appends a new revision of the same daily identity, with manager authority and reason.
7. **Failure/navigation:** 409 keeps the draft and offers reload/compare; never silently overwrites. Network ambiguity reuses the same command key. Permission loss clears protected in-memory data and cancels requests; current permission is checked on every retry. Switching estate/date/filter or leaving with a dirty row/form requires discard/save. No localStorage of personal information. Keyboard labels, focus restoration, status text and non-colour error cues are required.

## Data ownership and identity

Recommendation for review (D01): Operations owns both aggregates in its existing database, in separate worker/attendance packages and ports. This extends Operations from work to a small operational register; it is not an HR master. Estate remains authoritative for estate/division UUIDs/timezone, Keycloak for accounts/claims, Spatial for geometry, Analytics for future projections. A dedicated Workforce service is an alternative if cross-estate employment/payroll identity is required now; that would change this plan materially. No new repository, shared model, distributed transaction or cross-service foreign key is proposed.

Use `workerRegistrationId` (UUID) wherever new attendance refers to a registration. Worker resource `id` is that UUID. Existing Operations `workerId` remains signed-sub text, unchanged on disk/wire/events. No implicit mapping from matching code/name/username. WA-1 intentionally has no account-link column/endpoint or lookup dependency in tapping. It supports non-login staff for attendance, while assignment/execution continue under the current subject contract. Account linking and selecting registered people in tapping need a subsequent reviewed bridge contract with verified issuer+sub linkage, scope/revocation semantics and migration tests. If the owner requires that bridge now, revise and re-review this package before contracts.

| Proposed service-owned record | Fields and constraints |
|---|---|
| WorkerRegistration | `id`, `estateId` UUIDs; `workerCode` trim/uppercase ASCII `[A-Z0-9][A-Z0-9_-]{0,63}`; `displayName` trimmed Unicode 1..200; nullable `divisionId`; immutable `dataProvenance` REAL/SIMULATED; nonnegative `version`; created/updated UTC instants and signed-sub actors. Permanent unique `(estateId,workerCode)` across closed periods; no name uniqueness. Identity/estate/code/provenance immutable; no code reuse or silent reassignment to another person. |
| WorkerActivePeriod | UUID id, workerRegistrationId internal FK, `activeFrom` inclusive ISO date, nullable `activeTo` exclusive ISO date, introduction/closure revision. `activeTo > activeFrom`; no overlap per registration, at most one open interval. Root serializes changes. State at date is derived from periods, not an employment/legal status. No payroll or reason-for-leave classification. |
| WorkerRevision | `(workerRegistrationId,version)` unique; full minimal profile/period snapshot; command kind, change reason, actor, recordedAt, correlationId. Append-only. A prior revision is evidence, not the current eligibility view. |
| AttendanceDay | UUID id, estateId, workerRegistrationId internal FK, local attendanceDate, timezone snapshot, worker code/division and worker-version snapshot, matched activePeriodId; immutable provenance copied from registration; status PRESENT/ABSENT/EXCUSED/VOIDED; version and audit fields. Permanent unique `(estateId,workerRegistrationId,attendanceDate)` including voided evidence. No duration or zero-hour surrogate. |
| AttendanceRevision | `(attendanceId,version)` unique, full post-command snapshot, command kind RECORD/CORRECT/VOID/RERECORD, mandatory reason for all noninitial commands, actor/recordedAt/correlationId. Status correction preserves identity/context snapshots. Re-record keeps daily identity fixed but snapshots current validated eligibility/context into its new revision; earlier revisions retain their original context. Initial backdateReason and all change reasons are retained in protected revision evidence only. Void retains previous observation in history. |
| CommandReceipt / outbox | Reuse the established pattern, not necessarily the collection-specific tables: actor+key uniqueness across WA commands, canonical request hash, method/path, original success status/body/Location, aggregate/version; atomically persist root+revision+receipt+one outbox event. Keep sensitive command bodies out of logs. Retention must follow D09 rather than silently inheriting collection retention. |

Registration create/version starts at 0; each effective command increments once. No-op edit/correction is rejected; exact successful replay does not increment or emit. Exclusion constraints or serialized root locks plus DB uniqueness must enforce active-period and daily uniqueness under concurrent requests. Runtime role can update current roots but cannot update/delete immutable revisions; migration owner remains separate. Migration design must inspect existing grants, not assume new tables inherit the correct rights.

Initial registration accepts `activeFrom` today or earlier, not future; no automatic scheduled activation. Close end date is exclusive and may be at most estate-local tomorrow (meaning active through today), never a later scheduled closure. It must remain after activeFrom. Reactivation opens a new period starting today or earlier after the previous end; no overlap. Any historical period change requires manager reason and cannot invalidate any retained nonvoided attendance date (409). Same-database locking must serialize attendance creation/re-record against period close so this rule holds under races. Corrections/voids of existing attendance remain possible after registration/estate deactivation with current trusted estate authority; they do not require a live active parent.

For new registration/initial attendance/re-record, use authenticated bounded Estate GETs to validate active estate and canonical timezone; validate optional division through Estate API including ownership/status. No fake fallback if dependency is unavailable. Attendance also validates the registration is active on the requested date. Initial attendance/re-record must have date <= canonical estate-local today. Any past day requires manager authority and reason; supervisors may record today only. Corrections/voids require manager reason regardless of date; historical evidence is not silently shifted if estate timezone or division later changes. UTC microsecond timestamps and explicit offsets follow 3B precision convention. No client actor/recordedAt/timezone override.

No estimated/predicted attendance is allowed in WA-1: uncertainty stays UNMARKED. A worker registration's provenance cannot be switched from SIMULATED to REAL. REAL requires owner-confirmed facts and the privacy gate; creating a separate real record must not copy invented identity as confirmed. Provenance is an assertion, not certification of employment or physical presence.

Roster query is a current registration view for the requested date, not an immutable past roll-call sheet. Current name/division filters never rewrite recorded snapshots. `eligibleCount` counts current eligible registrations; `markedCount` counts those with nonvoided evidence; `unmarkedCount=eligibleCount-markedCount`; `voidedCount` counts eligible identities whose current evidence is VOIDED. Separately report `outsideRosterRecordedCount` for nonvoided evidence outside current eligibility, and label it for investigation. No row omission is interpreted as ABSENT. Date/provenance/scope predicates precede all totals and pagination. Do not promise a consistent multi-request traversal while data changes.

## Proposed authorization matrix

All permissions below require valid issuer/audience/signature/lifetime/sub. Except PLATFORM_ADMIN's explicit global permission, valid administrator-managed estate_ids must contain the target. PLANTATION_ADMIN's existing global Operations privileges are not automatically personal-data privileges. Positive permissions are checked per command/read; mixed roles add only explicitly granted abilities. No caller-supplied worker ID, directory record or default division grants access.

| Role | Minimal register/current attendance + roster | Register/edit/open/close periods | Record today's roll call | Backdate/correct/void/re-record | Immutable histories |
|---|---|---|---|---|---|
| PLATFORM_ADMIN | Global | Global | Global | Global | Global |
| ESTATE_ADMIN / ESTATE_MANAGER | Scoped | Scoped | Scoped | Scoped, reason | Scoped |
| FIELD_SUPERVISOR | Scoped minimal current view | Deny | Scoped | Deny | Deny |
| AUDITOR | Scoped | Deny | Deny | Deny | Scoped |
| VIEWER / FIELD_WORKER / AGRONOMIST | Deny | Deny | Deny | Deny | Deny |
| PLANTATION_ADMIN alone | Deny | Deny | Deny | Deny | Deny |

D06 must explicitly accept/revise this narrower policy, including PLATFORM_ADMIN/AUDITOR personal-data visibility. There is no finer division/block entitlement today; default division is a filter only. A supervisor+VIEWER remains a supervisor for these operations; a worker+VIEWER gains no registry visibility; a scoped manager+PLANTATION_ADMIN does not become global. Existing Operations endpoint policies remain unchanged. Unauthorized object requests return 403 without body details; missing authorized objects return 404. Resolve ownership with minimal metadata before loading evidence; list/search/count/history/replay must not expose other estates. Audit-view access should be observable without logging names/reasons/payloads. New scopes/roles require a separate identity review if existing estate scope is too broad.

## REST design for review

Author executable definitions only in Contracts after WA-T00 approval. Proposed additions to `openapi/operations-service.yaml`, preserving all 27 existing operations. Gateway will route `/api/v1/workers/**` and `/api/v1/attendance/**` to Operations with existing authentication/audience/timeouts/correlation conventions. No frontend direct service calls, BFF, WebSockets or new protocol.

All writes require UUID `Idempotency-Key`, JSON closed objects, explicit provenance on registration creation, and observed nonnegative root `version` on noncreate commands. Caller actor/scope/derived properties rejected. Reasons are trimmed 1..1000 characters; reject control characters and instruct users not to enter sensitive personal/health information. Responses use UTC timestamps, canonical UUIDs, explicit nullable optional fields, and version/audit fields. Specified shapes below are a wire proposal, not an executable/released contract.

| Method/path | operationId | Request / response |
|---|---|---|
| POST `/api/v1/workers` | registerWorker | `{estateId,workerCode,displayName,activeFrom,dataProvenance,divisionId?}` -> 201 WorkerView + Location |
| GET `/api/v1/workers` | listWorkers | Required estateId; optional activeOn date, normalized exact code, name prefix (1..100 Unicode), divisionId, provenance; page/size -> 200 WorkerPage. Omitted activeOn includes closed registrations; no future date. |
| GET `/api/v1/workers/{id}` | getWorker | -> 200 WorkerView incl. active periods; no attendance history embedded |
| PATCH `/api/v1/workers/{id}` | updateWorker | `{version,reason,displayName?,divisionId?}` -> 200 WorkerView. Omitted unchanged; only divisionId may be null to clear; at least one changed value. |
| POST `/api/v1/workers/{id}/close-period` | closeWorkerPeriod | `{version,activePeriodId,activeTo,reason}` -> 200 WorkerView |
| POST `/api/v1/workers/{id}/open-period` | openWorkerPeriod | `{version,activeFrom,reason}` -> 200 WorkerView |
| GET `/api/v1/workers/{id}/history` | getWorkerHistory | page/size -> 200 WorkerHistoryPage |
| GET `/api/v1/attendance/roster` | getAttendanceRoster | Required estateId,date,provenance; optional current divisionId, page/size -> 200 RosterPage incl. date/timezone, coverage counters and rows `{worker,attendance?}` |
| POST `/api/v1/attendance/days` | recordAttendanceDay | `{workerRegistrationId,attendanceDate,status,backdateReason?}` -> 201 AttendanceView + Location. Initial status PRESENT/ABSENT/EXCUSED; estate/provenance/timezone derived. |
| GET `/api/v1/attendance/days` | listAttendanceDays | Required estateId,from,to; optional workerRegistrationId,status,provenance; page/size -> 200 AttendancePage |
| GET `/api/v1/attendance/days/{id}` | getAttendanceDay | -> 200 AttendanceView |
| POST `/api/v1/attendance/days/{id}/corrections` | correctAttendanceDay | `{version,status,reason}` -> 200 AttendanceView; current nonvoided status must change |
| POST `/api/v1/attendance/days/{id}/void` | voidAttendanceDay | `{version,reason}` -> 200 AttendanceView; only nonvoided |
| POST `/api/v1/attendance/days/{id}/re-record` | rerecordAttendanceDay | `{version,status,reason}` -> 200 AttendanceView; only VOIDED, revalidates active period/date/estate; reuses original daily UUID; refreshes current eligibility/context snapshots in the new revision, preserving earlier revisions |
| GET `/api/v1/attendance/days/{id}/history` | getAttendanceHistory | page/size -> 200 AttendanceHistoryPage |

WorkerView maps registration identity/profile/periods/version and createdAt/updatedAt, excluding actor subjects, revision reasons and internal receipt hashes. AttendanceView contains identity/context/status/version and createdAt/updatedAt, excluding actor subjects and backdateReason; command reasons and prior states appear only in authorized HistoryEntry `{id,version,commandKind,reason?,recordedAt,recordedBy,correlationId,snapshot}`. Full snapshots use the same view shape; no mutable `current` flag on revisions. WorkerRosterItem contains id,code,displayName,nullable divisionId,provenance and version. All ordinary current views use the same minimal fields regardless of role; actor subjects and backdate/correction reasons are accessible only in manager/auditor history. Initial record response uses that same minimal AttendanceView; no receipt replay may bypass field-level policy. Exact field-level schema review is a WA-T01 gate.

Pages: content,page,size,totalElements; default page=0,size=20, max100; reject overflow and unknown filters. Worker order code,id; roster order code,id; attendance order date DESC,id ASC; history version ASC. Attendance list requires ordered inclusive date bounds with difference <=366 days, following the existing Operations convention (up to 367 dates); roster requires one date. Reject future observation filters for roster; history/list may query dates with no evidence and return empty, not fabricated records. No CSV export/bulk write or separate summary endpoint in WA-1. Coverage is one scoped snapshot per roster request, counted before pagination and separated by requested provenance; counts do not assert the plantation's total real workforce.

Replay: authorize current actor/estate/operation before returning a receipt. Same actor+key+normalized method/path/body replays original success status/body/Location even if current resource advanced; different command ->409. Reuse the key on ambiguity. Stable current GETs reconcile stale replay results. Persist only successful results. Permanent daily/code uniqueness prevents duplicates across actors/keys; do not reveal foreign-estate conflicting rows. All protected response shapes are fixed per operation/role policy; permission downgrade must deny replay rather than leak a previously fuller response.

Errors retain application/problem+json and correlationId: 400 syntax/unknown field/invalid reason/status/date/precision; 401 invalid authentication; 403 role/estate/backdate denial; 404 authorized local record missing; 409 stale version/duplicate code or day/overlap/history-invalidating close/key mismatch/bounded lock timeout; 422 missing/inactive/mismatched Estate/division reference; 503 bounded dependency timeout/malformed required master response. Sanitize unexpected 5xx. No SQL, names of inaccessible workers, receipt bodies or downstream payloads in errors. Canonical normalized inputs and stable error meanings must be tested, not inferred from schema validity.

## Event design and compatibility

Proposal: new `events/operations/workforce/v1` and matching examples with eventVersion=1. Globally unique event types/routes avoid existing tapping v1 and collections v2. No consumers or analytics projection are part of WA-1; publish only to explicitly provisioned durable acceptance bindings until consumers are reviewed. Never publish personal display names, worker codes or free-text reasons on the shared domain exchange. A workforce UUID/actor subject is still a personal identifier; broker/DLQ/backups/receipt retention remains subject to D09.

All new envelopes require eventId UUID, eventType literal, eventVersion=1, timestamp UTC, source=`agrosphere-operations-service`, correlationId UUID, estateId UUID, dataProvenance REAL/SIMULATED, aggregateId UUID, aggregateVersion nonnegative int64 and payload. Do not require blockId for estate-level workforce events. Trace context remains transport metadata. Envelope identity/provenance/version must match payload. Full snapshots below mean full *minimal event state*, not full private REST/audit state.

| Type / routing key on agrosphere.domain | Trigger and minimal snapshot |
|---|---|
| WorkerRegistrationCreated / `agrosphere.WorkerRegistrationCreated.v1` | Register, version0: registrationId,estateId,nullable divisionId, active periods with ids/dates,provenance,version; no name/code/account subject |
| WorkerRegistrationChanged / `agrosphere.WorkerRegistrationChanged.v1` | Profile/period command, version>=1; same snapshot plus previousVersion and changeKind PROFILE/PERIOD_CLOSED/PERIOD_OPENED; emits even for a private profile change with no changed public field |
| WorkerAttendanceRecorded / `agrosphere.WorkerAttendanceRecorded.v1` | First daily record, version0: attendanceId,workerRegistrationId,estateId,date,timezone snapshot,nullable divisionIdSnapshot,activePeriodId,workerVersionSnapshot,status,provenance,version |
| WorkerAttendanceChanged / `agrosphere.WorkerAttendanceChanged.v1` | Correction/void/re-record, version>=1: same snapshot plus previousVersion and changeKind CORRECT/VOID/RERECORD. VOIDED remains an explicit tombstone. |

No dual publication under any existing event type. One event per successful root revision in the same local transaction as receipt/audit/root. Reuse tested relay confirms/mandatory returns/capped retry/FAILED retention; verify it handles these block-free envelopes and separate namespaces. Broker outage does not undo a committed HTTP result. Stable eventId survives ACK-crash duplication. A future consumer must atomically deduplicate eventId with its own projection, apply only greater aggregateVersion, quarantine equal-version conflicting snapshots, retain void tombstones and reconcile gaps from authorized APIs. No summing change events, exactly-once claim or fabricated initial worker event for historical tapping subjects.

Contracts release version remains TBD until reviewed compatibility/release policy chooses it; do not assume 0.6.0 approval or a SemVer bump alone guarantees safety. Capture exact old artifact hashes and prove them unchanged. Reviewed executable artifacts and their hashes must be accepted for independent local release before producer/consumer pinning. New typed Web pins may be a reviewed Operations subset; they cannot silently include unsupported worker/attendance policies or import sibling files during build/runtime.
