## Complete milestone prompt

```text
AgroSphere - M3: Operations, workforce, inspections, alerts and IoT

Role and objective
Act as the lead engineer and integration owner. Complete remaining M3 connected demonstration and explicitly selected gaps, preserving the approved 3A/3B, WA, II, AN/privacy and TLM implementations.

Operating instructions
Read agrosphere-architecture/docs/milestones/DEVELOPMENT_CHECKPOINT.md and APPLICATION_DEVELOPMENT_WORKFLOW.md, the original roadmap/checklist, this milestone's existing decisions/evidence, and each affected AGENTS.md before changes. Inspect actual source, contract versions, Git status and tool availability; do not infer implementation from documentation.

Work exclusively on the named milestone and its necessary dependencies. Preserve twelve independent Git roots/builds/releases and service-owned databases; no parent build, shared persistence models, sibling source dependency or cross-service SQL. Preserve current Git work, accepted artifact bytes, old migrations, existing data and private configuration. Reuse installed/pinned per-repository toolchains; do not impose the PDF's historical Java version globally.

Use separately owned disposable SIMULATED fixtures with explicit ownership and cleanup. No production deployment, Git staging/commit/push/publication, REAL-data enablement, existing-stack/data/private-config/role/credential mutation, or AEO changes. Generated fixture credentials are permitted only within an actually approved package. Never claim test success, hardware performance, hosted CI or owner acceptance without evidence.

Before new implementation, prepare one concrete consolidated review for genuinely unresolved product, contract, security, provider, license and cost decisions. Complete authorized discovery and review preparation first. Recognize prior approvals; do not repeat them. After package approval, execute all included phases autonomously, including delegated conforming contract/local-release/pin/SQL engineering checks. Resolve routine reversible choices yourself. Stop only for a material decision outside scope or a genuine blocker; continue independent authorized work where useful.

For a public API/event change, specify actual operations/envelopes, validation/errors, idempotency, compatibility and security in Contracts; perform exact executable engineering review/local release before consumer pins under the package's delegated authority. Persist only in the owning service with additive migrations and preservation tests where relevant. Never invent endpoints or broaden roles from examples.

Deliver working behavior, actual commands/results, artifact identifiers, failures/retries, cleanup status and remaining limitations. Update the sole completion checklist and checkpoint, distinguishing engineering completion from owner acceptance. Stop at the selected milestone; do not start another automatically.

Repository responsibilities
Operations owns tapping/collections/DRC/workforce/inspections/incidents/in-app alerts; Telemetry owns device readings; Web/Gateway expose scoped workflows; Contracts/Infrastructure/Architecture support integration.

Domain and data ownership
Tapping schedules/assignments/execution, collection revisions and measurement provenance, worker attendance, inspections/manual incidents, in-app alert lifecycle, device registry and immutable sensor readings.

Functional and nonfunctional requirements
Verify tapping to latex/DRC traceability using current accepted collection semantics rather than the PDF's proposed batch APIs. Preserve exact decimal arithmetic, correction history and unknown versus zero. Verify attendance and manual inspection/incident flows, HIGH/CRITICAL inbox behavior, read/acknowledge/resolve/reopen/history and privacy states. Exercise authenticated generated MQTT through persistence/latest API and Web freshness. Map PDF 3E analytics and 3F overlays to existing ANL/TLM work rather than rebuilding them.

Security
Enforce worker self/estate/object authorization, signed identity and minimal sensitive logs. Retain default-disabled subject-policy gates, existing retention/redaction semantics, broker ACLs and owned-fixture boundaries. No real workforce or external notifications.

Required automated and integration verification
Run selected Operations/Telemetry/Web suites and contract regressions; prove transactional outbox, duplicate/out-of-order/restart recovery, invalid/device/cross-estate denial, concurrent writes and preserved nonempty migrations. Execute the connected generated alerts/privacy and MQTT walkthrough with owned cleanup.

Working demonstration
Use generated identities to record work and latex/DRC, raise an inspection/incident and in-app alert, acknowledge/resolve it, publish simulated weather/soil telemetry and inspect values/freshness on the correct block.

Material decision boundary
Consolidate demo-relevant WA D08/D09, II D07/D08, AN D07/D08 and privacy maintenance/copy conditions in the existing client register. Real-subject/legal/production portions remain outside generated delivery; do not invent policy facts.

Execution phases
1. Discovery and prerequisites: Reconcile 3A/3B/WA/II/AN/TLM evidence and the PDF 3A-3G mapping.
2. Domain, contracts and consolidated review: Prepare one connected M3 scope/policy/workload and verification review.
3. Implementation: Implement only approved gaps in owning Operations/Telemetry domains and migrations.
4. Integration: Integrate actual outbox/MQTT/Gateway/PKCE/Web behavior in owned fixtures.
5. Quality and demonstration checks: Verify connected alerts/privacy/telemetry plus concurrency, denial, replay and cleanup.
6. Documentation and reproducibility: Update workflow/state diagrams, retained policy decisions and demo instructions.
7. Completion and handoff: Deliver the connected M3 walkthrough and record capability-level acceptance.

Definition of Done
- All in-scope requirements map to actual working behavior and executed evidence.
- Changed public artifacts are independently reviewed/released/pinned as authorized.
- Applicable authorization, isolation, replay/recovery and preservation checks pass.
- The working demonstration is reproducible and owned resources are cleaned up.
- Unavailable physical hardware, failed tests and unresolved requirements stay explicit.
- Source/pins, actual check results, limitations and checkpoint are current.
- Owner functional acceptance is recorded only from an explicit owner response.

Completion report
Report ENGINEERING COMPLETE / PARTIAL / BLOCKED, separately from OWNER ACCEPTANCE.
List repositories/files changed, domain/API/event/migration changes, demonstration
steps/results, commands and actual pass/fail/unavailable results, artifact identities,
cleanup, remaining limitations and the next owner-selectable prompt. Documentation
alone never completes implementation. Do not begin another milestone.
```

prompt runs approved phases consecutively without requiring seven separate approvals.
Each block loads the full milestone specification above and narrows execution to one
phase. If a prerequisite or material approval is absent, make the gap concrete and
stop dependent work. A phase prompt never overrides an unapproved decision.
